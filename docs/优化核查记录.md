## 性能实测

同一 Node 进程中对旧、新引擎交替计时；预热 5 次、采集 15 次取中位数。下表请求同样的点数据和三种导出格式，用来观察计算改动，而非仅靠省略输出获得加速。

| 工作负载 | 基线 / ms | 优化后 / ms | 比值 |
| --- | --- | --- | --- |
| 720 目标分辨率 | 5.25 | 4.15 | 约 1.27 倍 |
| 4000 目标分辨率 | 77.19 | 33.01 | 约 2.34 倍 |
| 示例基圆搜索 | 7.03 | 4.04 | 约 1.74 倍 |
| 128 段程序 | 6.07 | 4.12 | 约 1.47 倍 |

4000 分辨率案例的旧完整响应约 2.41 MB；新默认响应约 1.33 MB，仅摘要约 842 字节。完整选择全部格式时仍有约 2.40 MB，因为这是使用者明确要求的数据。输入副本不是同一轮廓的重复序列化，但默认关闭它可减少体积并避免无意回显。

计时受机器、JIT、输入形状和输出选择影响。分桶在大量长包围盒重叠时仍可能退化，以上不是最坏复杂度或普遍加速保证。

## 重现

```sh
npm run build
npm run test:integration
python tests/oracle.py
python -m pip install -r requirements-test.txt
python tests/dxf_interop.py
npm run benchmark
```

对照旧版本时，在独立工作树构建基线，再运行：

```sh
git worktree add --detach artifacts/baseline 2fb4476
cd artifacts/baseline
npm run build
cd ../..
node tests/benchmark.mjs artifacts/baseline/web/engine.js
```

脚本写入 artifacts/performance.json。新的基础测试覆盖标量/完整结果一致、分段采样与二分查询一致、交叉算法差分、失败状态、输入字节边界、CLI 退出码、紧凑报告与按需格式。

## 仍需明确的边界

完成的零交叉检查只排除了采样折线的严格交叉，没有证明连续轮廓的相切、共线重叠、采样间回环或远处滚轮干涉不存在。DXF 独立读取只验证特定读取器的互操作，不替代商业 CAD 或加工验证。
